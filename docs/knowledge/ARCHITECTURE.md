Approved pilot target: keep the existing household assistant unchanged and add two independent, narrow ADK applications for managed Agent Runtime. `surplus-intake` accepts bounded text/image/audio and emits a typed candidate only. `collection-planner` accepts a verified NGO request plus a backend-supplied eligible surplus snapshot and emits a typed stop proposal only. Neither agent owns Firebase identity, authorization, canonical writes, eligibility, quantities, reservations, dispatch or route calculations. FastAPI remains the authority; Firestore owns confirmed records; the Google Maps Routes API supplies route facts. The web adds secondary `/surplus`, `/ngo/login` and `/ngo` routes with demo-only labels and actual map rendering. Household scope and NGO scope are disjoint and fail closed.

Planned: Next.js/App Hosting; FastAPI/Cloud Run canonical authority; real Gemini and one ADK orchestrator; managed Sessions and consented Memory Bank; preferred managed Runtime. Fallback needs concrete blocker and equivalent proof. Firestore owns confirmed facts/actions/outcomes; memory stores approved preferences. Five typed cards. Private owner-recorded sharing log; real community/commerce operations deferred.

Current implementation: Next.js 16.4.1, React, Tailwind v4. Home, Kitchen, Ask, Shop, Activity, and Settings no longer consume the synthetic browser store. The four destinations use a shared tab-scoped Firebase identity/household selection and canonical Kitchen, Shop, Activity, or assistant endpoints; unauthenticated, empty, unavailable, and error states are explicit. A separate `/account` route provides household reads, manual facts, shopping commands, actual-outcome recording, owner-reported private sharing and paginated private history. Saved meal-plan follow-ups can record an explicitly observed item outcome with a backend-validated same-household plan reference; approval still does not imply preparation or consumption. All browser writes share the default-off `NEXT_PUBLIC_ECOLOOP_ENABLE_COMMANDS` gate. `/kitchen/add` supports manual, bounded text, and bounded transient-photo candidate intake; candidate records do not change canonical Kitchen facts. Photo bytes are not persisted. A separate private-media API supports owner-scoped upload, metadata read and deletion when a matching bucket is configured, but the browser does not use it and no object-expiry cleanup is configured. Kitchen item detail includes a default-off, versioned correction form; authenticated UI acceptance remains open. Owner-private preference controls are available. The opt-in managed Memory Bank adapter is disabled by default and unverified. Five fixed assistant card renderers are wired to Ask; durable private proposal history, dismissal, BuyCheck shopping approval, explicit meal-plan approval and deterministic eligible-quantity scaling are implemented locally. Model-suggested portion amounts are preview-only; Kitchen stock is never changed by meal-plan actions. A shared bounded allowlisted transport never automatically retries writes. Identity/household changes cancel requests and scope-keyed data prevents previous-household records being displayed during a switch. FastAPI verifies Firebase identity plus explicit active household membership; scoped Firestore transactions include version checks, actor-bound idempotency and payload fingerprints. Owner-private share logs and activity APIs add atomic handover outcomes, scoped pagination and household-timezone expiry checks. Client Firestore/Storage rules deny access by default. Backend settings can load ignored `backend/.env`, but provider calls remain explicitly disabled unless `AGENT_ENABLED=true`; health reports configuration only and does not probe providers. Assistant defaults to temporary in-process ADK sessions. Opt-in managed Sessions and Memory Bank adapters are implemented locally but unverified; managed Agent Runtime remains absent. The single ADK agent has authenticated, household-scoped read-only pantry, active-shopping and saved-meal-plan tools; each tool rechecks current membership and session scope is supplied by the verified API principal. Contextual item outcome/share flows and Shop add/update/archive commands are integrated; authenticated browser write acceptance remains open. See backend-foundation.md and the latest session for exact limitations.
Activity summarizes only its loaded owner-private outcome and sharing pages: measured amounts are grouped by exact unit, estimated/unknown amounts stay outside totals, and current offers remain distinct from reported handovers.
