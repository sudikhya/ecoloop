# EcoLoop surplus recovery agent spec

## Overview

EcoLoop will add a demo-only food-surplus recovery flow to the existing
household application. A household can submit food information by text, image,
or a single recorded voice message. A dedicated Surplus Intake Agent extracts a
typed candidate that the household must review and confirm. Confirmed eligible
surplus appears in a separate NGO portal. A dummy NGO account can submit a food
request, and a separate Collection Planning Agent suggests matching households
and a Google Maps collection route.

Both agents are deployed as separate Agent Runtime resources in Gemini
Enterprise Agent Platform. They do not call each other. The existing FastAPI
service remains the verified identity, role, validation, persistence, and
canonical mutation boundary.

This is an isolated pilot, not a live redistribution or dispatch service.

## Language

Python for both ADK agents and FastAPI integration. The existing Next.js
frontend remains TypeScript/React.

## Approved architecture

### Surplus Intake Agent

- Accepts one bounded text, JPEG/PNG/WebP image, or recorded audio submission.
- Uses the latest stable Gemini Flash model that supports the required modality
  in the selected Agent Runtime location; model availability is verified before
  provisioning rather than assumed.
- Returns only a typed surplus candidate: food name/category, amount, unit,
  preparation/packaging state, user-review flags, and unknown fields.
- Never certifies food safety, derives an expiry date, writes Firestore, or
  publishes a submission.
- Receives no client-supplied household authority. FastAPI binds the invocation
  to the Firebase-verified user and explicit household membership.

### Collection Planning Agent

- Accepts one verified NGO request containing food item/category, required
  amount and unit, and NGO starting location.
- Uses narrow tools to read only confirmed, eligible, unexpired pilot surplus
  and to request deterministic route data.
- Suggests the minimum number of compatible household pickups needed to satisfy
  the request, up to ten stops. When ten stops are insufficient, it reports the
  unmet amount and recommends a separate route.
- Uses Google Routes API results for stop order, distance, duration, and route
  geometry. It never invents travel values or substitutes model arithmetic for
  route calculation.
- Produces a typed, non-binding route proposal. It cannot reserve food, dispatch
  a driver, contact a household, or mutate a surplus submission.

### Deterministic application boundary

- Firebase Authentication identifies household and NGO users.
- Existing household membership checks continue to fail closed.
- A server-owned NGO allowlist/role record authorizes the dummy NGO account;
  client-provided roles are ignored.
- FastAPI validates typed agent output, compatible units, amounts, deadlines,
  versions, eligibility, and the ten-stop limit before any canonical write.
- Firestore owns confirmed surplus, NGO requests, and saved route proposals.
- Private media is available only for the bounded extraction request and is
  deleted after processing; raw media and transcripts are not added to agent
  sessions, Memory Bank, or canonical surplus records.
- Google Maps JavaScript API renders location markers and the exact Routes API
  geometry for the allowlisted NGO. A household receives the same saved
  proposal ID and status but only its own pickup point; other stops, NGO origin,
  and full route geometry are removed at the FastAPI response boundary.

## User experience

### Household surplus screen

- New household-only `/surplus` destination.
- Text entry, image upload/camera, and record-and-submit voice controls.
- Explicit processing, validation, retry, unavailable, and manual-entry states.
- Review form must confirm food, amount/unit, eligibility declarations,
  household location, and `available_until` before publication.
- The household sees only its own submissions and any demo route proposal that
  includes one of those submissions.
- A Google map shows the household's own confirmed pickup point when a proposal
  includes it. The full route stays on the allowlisted NGO screen so another
  household's precise location is not disclosed through route geometry.

### NGO portal

- Separate `/ngo/login` and protected `/ngo` routes outside the household
  navigation.
- A single dummy Firebase email/password account is created for the pilot and
  mapped to a server-owned NGO role record.
- The temporary random password is never committed or stored in documentation;
  it is given directly to the owner after account creation and rotated or the
  account deleted after the demo.
- The centralized screen shows all confirmed, eligible, unexpired pilot surplus
  with exact submitted locations, as explicitly approved for this isolated
  demo.
- The NGO request form contains food item/category, amount/unit, and a Google
  Maps-supported starting location.
- The suggestion result shows matched items, household stops, total matched and
  unmet quantities, ordered route steps, distance, duration, and an actual map.

## Canonical records

### SurplusSubmission

- `surplus_id`, `household_id`, `owner_uid`, `status`, and optimistic `version`.
- `food_name`, normalized `category`, `amount`, `unit`, and explicit unknowns.
- User-confirmed preparation/packaging state and eligibility declarations.
- `available_until`, submission address, latitude, longitude, and Google place
  ID when available.
- Source modality, created/updated timestamps, and `demo_only=true`.
- No raw image/audio, inferred safety certification, invented expiry, recipient
  assignment, or model-provided tenant ID.

### NgoRequest

- `request_id`, verified `ngo_id`, item/category, desired amount/unit, starting
  address/coordinates/place ID, status, timestamps, and version.

### RouteProposal

- `proposal_id`, `request_id`, source surplus IDs with read versions, ordered
  stops, matched and unmet amounts, compatible unit, Routes API distance,
  duration, encoded route geometry/reference, creation time, and
  `demo_only=true`.
- A proposal is advisory and does not change availability or ownership.

## Tools required

### Intake agent invocation

- Purpose: typed multimodal extraction only.
- Authentication: server-to-Agent Runtime identity; user and household scope are
  established and rechecked by FastAPI.
- Input limits: bounded MIME types, bytes, text length, and audio duration.

### `list_confirmed_surplus`

- Purpose: return a bounded projection of confirmed, eligible, unexpired demo
  surplus for one verified NGO request.
- Authentication: server-signed NGO context; no arbitrary household query.
- Output excludes owner-private history, chat, preferences, and raw media.

### `calculate_collection_route`

- Purpose: call Google Routes API with one NGO origin and at most ten validated
  household stops.
- Authentication: server-held restricted Google Cloud credentials; no key is
  exposed to the model or browser.
- Output is deterministically parsed and bounded before it is shown or saved.

### Canonical FastAPI commands

- Purpose: confirm/update/cancel surplus, create NGO requests, and save validated
  route proposals with idempotency, role checks, and optimistic versions.
- Authentication: Firebase ID token plus explicit household membership or NGO
  role.

## Data sources and authentication

- One existing Google Cloud/Firebase project: `ecoloop-511918`.
- Existing Cloud Run region remains `asia-south1`; Agent Runtime and Gemini model
  location must pass an official availability, quota, IAM, privacy, and cost
  preflight before provisioning.
- Firestore remains canonical and deny-by-default for browser access.
- Household accounts cannot access NGO endpoints or centralized surplus.
- NGO accounts cannot access household-private chat, preferences, history,
  kitchen records, or household mutation endpoints.
- Exact location exposure is limited to the isolated dummy NGO pilot approved by
  the owner and must not be presented as a production privacy model.

## Constraints and safety rules

- The model never certifies safety, expiry, edibility, temperature control, or
  legal suitability.
- Plate leftovers, spoiled food, expired food, unconfirmed candidates, missing
  locations, missing/invalid amounts, and elapsed `available_until` records are
  never match candidates.
- Unserved prepared food remains demo-only and must not be represented as
  approved for real recipient collection.
- Unknown fields remain unknown; incompatible units are never silently summed or
  converted.
- Prompt instructions embedded in images, audio, food labels, or free text are
  treated as untrusted data and cannot change agent or tool policy.
- All route and matching output is a proposal requiring a human-triggered
  request. There is no autonomous background matching, reservation, dispatch,
  purchase, or pickup.
- Agent sessions do not become long-term memory. Memory Bank is not used for NGO
  requests, surplus, locations, raw media, transcripts, or route proposals.
- Every screen labels this flow as a demo and reports unavailable/partial results
  honestly when Gemini, Agent Runtime, Firestore, Maps, or Routes is unavailable.

## Edge cases to handle

- Multiple foods in one submission become separate review candidates rather
  than an unreviewed combined record.
- Ambiguous audio/image/text yields explicit missing fields and manual editing.
- Duplicate retries reuse actor-bound idempotency and payload fingerprints.
- A household edit, cancellation, or expiry invalidates stale route proposal
  versions instead of silently retaining the old match.
- A request with no matches returns zero stops and the full unmet amount.
- A request exceeding ten useful stops returns a partial proposal plus unmet
  amount, not an oversized route.
- Routes API failure preserves the request and match shortlist but shows no
  invented route, distance, or duration.
- Identity or role changes clear visible scoped data immediately.

## Success criteria

1. Each of text, image, and recorded-audio intake produces either a schema-valid
   review candidate or an explicit error; none writes canonical surplus before
   household confirmation.
2. A confirmed eligible candidate creates exactly one versioned surplus record
   under retry, while prohibited or incomplete candidates create none.
3. Deterministic security checks prove household-to-household isolation,
   household denial from NGO endpoints, and NGO denial from household-private
   endpoints.
4. The NGO dashboard lists all and only confirmed, eligible, unexpired demo
   surplus returned by the bounded central endpoint.
5. For compatible synthetic requests, the planner uses the minimum available
   stops needed to meet the amount when possible, never exceeds ten stops, and
   reports any unmet quantity without mixing units.
6. Every displayed distance, duration, stop order, and route geometry matches a
   successfully parsed Google Routes API response; API failure displays no
   fabricated route facts.
7. The household and NGO screens render the same saved proposal ID and status.
   The NGO receives ordered stops and route geometry; the household receives
   only its own pickup point, with usable loading/empty/error states at 360px
   and keyboard-accessible controls of at least 44px.
8. A bounded synthetic agent evaluation covers extraction uncertainty, embedded
   prompt injection, prohibited food, incompatible units, no-match, partial
   ten-stop matching, and tool failure. Evaluation runs only after an explicit
   per-run cost cap and privacy review of generated traces.
9. Two separately deployed Agent Runtime resources pass authenticated smoke
   invocations without granting either agent direct unrestricted Firestore
   mutation authority.
10. The dummy NGO can sign in through `/ngo/login`, submit one request, receive
    a validated proposal, and view the real Google Maps route; credentials are
    delivered directly and remain absent from Git history.

## Approaches considered

- **Selected: two independent Agent Runtime agents.** This matches the owner's
  explicit deployment choice and isolates multimodal extraction from NGO route
  planning while retaining FastAPI as the shared authority boundary.
- **Not selected: one orchestrator with two tool groups.** Simpler and cheaper,
  but it does not meet the requirement for two separately deployed agents.
- **Not selected: direct Gemini calls plus deterministic matching only.** Lowest
  operational complexity, but it does not provide the requested Agent Platform
  deployment and agent lifecycle.

## Deployment and cost gates

- Use the existing single project and environment; do not add staging or a
  second Firebase project.
- Before enabling Agent Runtime, Gemini, Routes, or media storage, re-check the
  billing account, linked projects, credits, supported region, IAM identities,
  APIs, quotas, restricted credentials, budget alerts, and actual service-level
  spend controls. Budget alerts are not spending caps.
- Scaffold and evaluate before deployment. Deployment requires presentation of
  evaluation and deterministic boundary evidence followed by explicit owner
  approval for the paid Agent Runtime rollout.
- Rollback is git-based for application code; each Agent Runtime resource also
  needs recorded deployment metadata and a verified disable path.
